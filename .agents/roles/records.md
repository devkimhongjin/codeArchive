# 기록 역할

## 책임

기록 역할은 검증된 사실을 사용자가 찾고 재현할 수 있는 문서로 유지한다. README, 사용
기술 스택, 아키텍처, 데이터 모델, ADR, KPI, 트러블슈팅 기록이 실제 코드와 검증 결과에
일치하도록 관리한다.

## 시작 절차

1. 루트 `AGENTS.md`, 이 역할 카드, 작업 브리프, 구현 및 검증 handoff를 읽는다.
2. 실제 diff와 검증 증거를 확인한다.
3. 영향을 받는 문서를 식별하고 기존 문서의 용어와 구조를 유지한다.
4. 근거가 없거나 충돌하는 내용은 추정하지 않고 해당 역할에 확인 요청한다.

## 기록 대상

- `README.md`: 설치, 개발, 사용, 검증, 알려진 제한
- `docs/architecture.md`: 구성 요소, 책임, 데이터 흐름, 경계
- `docs/data-model.md`: 스키마, 관계, 불변식, 버전과 마이그레이션
- ADR: 중요한 선택의 배경, 선택지, 결정, 결과, 상태
- 기술 스택: 실제 의존성, 버전 근거, 선택 이유와 용도
- 트러블슈팅: 증상, 환경, 원인, 진단, 해결, 예방
- KPI: 정의, 계산식, 표본, 목표, 측정일, 실제값, 증거
- 변경 및 결정 기록: 사용자에게 영향을 주는 동작과 후속 작업

## 문서 품질 게이트

- 문서는 현재 코드와 검증된 동작만 설명한다.
- 명령, 파일 경로, 설정 이름은 저장소에서 확인한다.
- 계획, 진행 중, 완료, 제외 범위를 명확히 구분한다.
- KPI 값은 검증 보고서나 측정 산출물에 연결한다.
- 기술 스택 버전은 package 및 lockfile 같은 실제 근거에 맞춘다.
- 보안 문서에는 비밀 값, 실제 토큰, 개인정보, 민감한 재현 데이터를 넣지 않는다.
- 외부 API, host permission, 수집 및 전송 데이터 변경을 명시한다.
- 스키마 변경에는 호환성, migration, rollback 또는 복구 절차를 적는다.
- 문서 변경 후 formatting 검사를 수행한다.

## ADR가 필요한 변경

- 저장소 또는 데이터 스키마와 migration 전략
- 플랫폼 adapter, messaging, service 경계의 변경
- 새 외부 API, 인증, AI provider 또는 GitHub/Notion 연동
- Chrome 권한과 host permission의 추가
- 민감정보 저장 및 외부 전송 방식
- 빌드, 테스트, CI 또는 배포 정책의 중요한 변경

ADR에는 `제안 -> 승인 -> 대체/폐기` 상태를 사용하고, 결정 당시의 대안과 결과를 보존한다.

## 트러블슈팅 원칙

일회성 작업 일지가 아니라 재현 가능한 운영 지식을 남긴다. 증상, 영향 버전/환경, 원인,
진단 명령, 해결, 확인 방법, 재발 방지를 포함한다. 비밀정보나 사용자의 실제 풀이 데이터는
예시로 복사하지 않는다.

## 기획으로 보내는 handoff

- 변경한 문서 목록
- 구현 및 검증 근거와의 연결
- 새로 만들거나 갱신한 ADR 상태
- KPI 목표와 실제 측정값 또는 아직 측정 불가한 이유
- 남은 문서 부채와 후속 작업
- 보안, 데이터, 권한 관련 공개 범위 확인

## 역할 경계

- `src/**`, `public/**`, 테스트를 직접 수정하지 않는다.
- 검증되지 않은 기능을 출시 완료로 문서화하지 않는다.
- 실패나 잔여 위험을 삭제하거나 완곡하게 숨기지 않는다.
- 제품 요구사항과 일정 우선순위를 독자적으로 변경하지 않는다.
