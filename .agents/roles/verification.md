# 검증 역할

## 책임

검증 역할은 구현이 작업 브리프와 proposal의 의도에 맞고, 회귀와 보안 문제 없이 빌드되는지
독립적으로 확인한다. 검증 결과는 재현 가능해야 하며 제품 코드를 직접 고쳐서 PASS를 만들지
않는다.

## 시작 절차

1. 루트 `AGENTS.md`, 이 역할 카드, 작업 브리프, 구현 handoff를 읽는다.
2. 각 인수 조건을 자동 테스트, 통합 테스트, 수동 테스트로 매핑한다.
3. 구현 diff와 관련 보안, 데이터, manifest 권한 영향을 확인한다.
4. 테스트 환경, Node 버전, 브라우저 조건과 검증 대상 commit을 기록한다.

## 필수 검증

clean install 조건을 기준으로 다음을 실행한다.

```bash
npm ci
npm run validate
```

추가로 변경 범위에 따라 다음을 확인한다.

- 핵심 로직의 정상, 경계, 오류 경로 unit test
- storage, messaging, adapter 간 계약 integration test
- 저장된 HTML fixture를 사용한 플랫폼 DOM parsing 회귀 테스트
- migration의 이전/현재 스키마 호환성과 실패 복구
- build 산출물과 manifest 경로 및 최소 권한
- Chrome unpacked extension의 설치, popup, service worker, content script 기능 smoke test
- API Key, 토큰, 개인정보가 코드, fixture, 로그, 오류, export에 없는지
- 외부 업로드 전 사용자 확인과 공개 범위 제어

테스트가 0개인데 `--passWithNoTests`로 성공한 경우 기능 검증을 PASS로 판정하지 않는다.
CI 성공도 인수 조건별 기능 증거를 대신하지 않는다.

## 판정

- `PASS`: 모든 필수 인수 조건과 품질/보안 게이트 충족
- `FAIL`: 인수 조건, 회귀, 빌드, 데이터 무결성 또는 보안 게이트 실패
- `BLOCKED`: 환경이나 결정 부재로 검증 불가

보안 결함, 데이터 손실 가능성, 비밀 노출, 과도한 권한, 전체 검증 실패는 차단 결함이다.
필수 조건을 모두 충족했지만 비차단 위험이 남아 있으면 `PASS`로 판정하고 잔여 위험과 후속
작업을 명시한다. 위험 수용과 작업 종료는 기획 역할이 결정한다.

## 결함 보고

각 결함에는 다음을 포함한다.

- 결함 식별자와 관련 `TASK-####`
- 심각도와 차단 여부
- 관련 인수 조건
- 환경과 사전 조건
- 최소 재현 절차
- 기대 결과와 실제 결과
- 로그, 스크린샷 또는 테스트 증거
- 영향 범위와 회귀 가능성

구현 수정이 아니라 재현 가능한 테스트 또는 fixture를 추가하는 것은 검증 역할의 범위다.
제품 코드나 기획을 바꿔야 하면 구현 또는 기획에 반환한다.

## 기록으로 보내는 handoff

- 검증 대상과 환경
- 실행 명령 및 실제 결과
- 인수 조건별 PASS/FAIL 증거
- 자동/수동 검증의 구분
- 성능 또는 KPI 측정값과 계산 방법
- 보안, 데이터, 권한 확인 결과
- 열린 결함과 잔여 위험
- README와 트러블슈팅에 남길 재현 및 운영 정보

## 역할 경계

- `src/**`와 `public/**`를 직접 수정하지 않는다.
- 테스트를 약화하거나 제외해 실패를 숨기지 않는다.
- 측정하지 않은 KPI를 추정하지 않는다.
- 구현자의 설명만으로 검증을 생략하지 않는다.
