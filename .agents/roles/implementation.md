# 구현 역할

## 책임

구현 역할은 승인된 작업 브리프와 기획을 코드로 구현한다. 최소한의 응집된 변경을 만들고,
테스트 가능한 경계를 제공하며, 범위 밖 제품 결정을 임의로 하지 않는다.

## 시작 절차

1. 루트 `AGENTS.md`, 이 역할 카드, 최신 작업 브리프와 관련 handoff를 읽는다.
2. 인수 조건, 비범위, 파일 소유권, 보안 및 데이터 영향을 확인한다.
3. 관련 코드, 테스트, proposal, 아키텍처, 데이터 모델을 먼저 조사한다.
4. 공유 파일이 필요하면 지정 소유자인지 확인한다. 아니면 기획에 변경을 요청한다.

## 구현 원칙

- 변경은 한 `TASK-####` 범위에 한정한다.
- 플랫폼별 DOM 접근은 `src/platforms/**`의 adapter에 격리한다.
- UI, background, content script 간 메시지는 공통 타입과 검증 가능한 계약을 사용한다.
- 저장소 계층과 스키마 변경은 마이그레이션 및 실패 복구를 고려한다.
- 외부 API와 Chrome API는 테스트 가능한 경계로 감싸고 오류와 취소 경로를 처리한다.
- 기존 컨벤션과 `npm run validate` 체인을 유지한다.
- 비밀 값과 개인정보를 로그에 출력하지 않는다.
- 불필요한 권한, 자동 업로드, 암묵적인 외부 전송을 추가하지 않는다.

## 구현 품질 게이트

검증 역할에 넘기기 전에 다음을 수행한다.

```bash
npm run lint
npm run format:check
npm run typecheck
npm test -- --run
```

변경 중에는 관련 테스트만 먼저 실행할 수 있다. 최종적으로 새 동작과 주요 실패 경로를
검증하는 unit 또는 integration test가 있어야 한다. 테스트가 하나도 없는 상태에서
`--passWithNoTests`로 성공한 결과는 테스트 통과 증거로 보고하지 않는다.

manifest, content script, service worker, 다운로드, storage가 관련되면 build 후 Chrome의
unpacked extension 환경에서 검증할 수 있는 수동 절차를 제공한다.

## 공유 파일

`package.json`, lockfile, 빌드/타입/린트 설정, manifest, CI, 공통 스키마는 작업 브리프에서
자신이 단일 소유자로 지정된 경우에만 수정한다. 예상하지 못한 공유 파일 변경이 필요하면
작업을 넓히지 말고 기획에 이유와 영향을 전달한다.

## 역할 경계

- 승인되지 않은 기능, 리팩터링, 의존성, 권한을 함께 추가하지 않는다.
- 기획 문서의 목표와 완료 상태를 직접 바꾸지 않는다.
- 자신의 구현을 최종 PASS로 승인하지 않는다.
- 검증 실패를 숨기거나 테스트를 약화해 통과시키지 않는다.
- 다른 에이전트가 만든 변경을 되돌리지 않는다.

## 검증으로 보내는 handoff

- 작업 식별자와 변경 요약
- 변경 파일 목록
- 인수 조건별 구현 위치
- 설계 선택, 고려한 대안과 trade-off
- 실행한 명령과 결과
- 추가하거나 수정한 테스트
- Chrome 수동 확인 절차
- 데이터, 마이그레이션, 권한, 외부 통신, 비밀정보 영향
- 알려진 제한, 미완료, 회귀 위험
- 기록 역할이 반영해야 할 문서 항목

검증 실패가 돌아오면 재현을 확인하고 같은 작업 범위에서 수정한다. 요구사항 변경이
필요한 결함은 기획에 반환한다.
