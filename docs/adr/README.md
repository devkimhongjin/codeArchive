# Architecture Decision Records

ADR은 되돌리기 어렵거나 여러 기능에 영향을 주는 기술·아키텍처 결정을 보존한다.

## ADR이 필요한 경우

- 저장 구조나 데이터 마이그레이션 변경
- 플랫폼 adapter, 메시징, background/content 경계 변경
- Chrome 권한 또는 외부 서비스 연동 추가
- 프레임워크, 테스트 도구, 배포 방식 도입·교체
- 보안·개인정보·오프라인 정책 변경
- 품질 임계치의 장기 예외

작은 일정·범위 결정은 `docs/project/decision-log.md`에 기록한다.

## 파일명과 상태

- 파일명: `NNNN-short-kebab-title.md`
- ID: `ADR-NNNN`
- 상태: `proposed`, `accepted`, `superseded`, `deprecated`, `rejected`
- 템플릿: `.agents/templates/adr.md`

번호는 기존 최대 번호 다음을 사용하며 재사용하지 않는다.

## 절차

1. 기획 또는 구현 에이전트가 맥락, 기준, 대안을 작성한다.
2. 구현·검증·기록 관점에서 결과와 측정 방법을 검토한다.
3. 승인자를 명시하고 `accepted`로 변경한다.
4. task brief, 구현 인계서, 검증 보고서에서 ADR을 연결한다.
5. 결정이 바뀌면 원본을 삭제·개작하지 않고 새 ADR에서 대체한다.

## 품질 기준

- 결정 전에 검토한 현실적인 대안이 둘 이상 있다.
- 장점뿐 아니라 비용, 위험, 롤백 방법을 적는다.
- 확인된 사실과 가정을 구분한다.
- 관련 KPI와 실패/철회 조건을 포함한다.
- 외부 자료는 원문 링크와 확인 날짜를 남긴다.
