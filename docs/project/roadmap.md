# CodeArchive 로드맵

> 상태: 초안(Draft)  
> 운영 단위: 1주 스프린트  
> 날짜와 출시 목표: 미확정

이 로드맵은 제안서의 12단계 개발 순서를 의존성 중심 마일스톤으로 재구성한 것이다. 각 마일스톤은 기간 약속이 아니라 작업 순서와 검증 관문을 나타낸다.

## M0. 기반 정렬 — 현재

목표는 기능 구현에 앞서 데이터, 아키텍처, 검증과 변경관리의 공통 기준을 만드는 것이다.

포함 범위:

- 프로젝트 제어 문서와 백로그
- 핵심 엔터티 및 식별자 초안
- 플랫폼 어댑터 계약과 fixture 전략
- IndexedDB 스키마 및 마이그레이션 전략
- 테스트가 실제로 존재해야 통과하는 검증 관문
- KPI 측정 방법과 보안 결정 대기 목록

종료 조건:

- 초기 결정 대기 항목의 담당과 해소 방법이 정해진다.
- Problem, SolutionSession, Submission, AIUsageRecord의 규격이 검토된다.
- 자동 검증이 최소 한 개 이상의 실제 테스트를 실행한다.
- M1 후보 작업의 의존성, 수용 기준과 검증 방법이 준비된다.

현재 이 조건들은 완료로 확인되지 않았으므로 M0는 진행 전/정렬 상태로 유지한다.

## M1. 데이터 규격과 기존 풀이 추가

제안서 단계 1~2에 대응한다.

포함 범위:

- 문제, 풀이 세션, 제출, AI 활용 데이터 규격
- JSON과 Markdown 가져오기 규격
- 파일명과 중복 판별 규칙
- 직접 등록, 코드 붙여넣기, 단일 파일, 코드 없는 문제 등록
- 기록 수정·삭제와 중복 검사

종료 조건:

- 정상·오류·중복 입력을 테스트한다.
- 데이터가 브라우저 재실행 후 유지된다.
- 기존 풀이 수동 등록 1분 이내 목표의 측정 절차가 정의된다.
- 스키마 변경과 복구 절차가 문서화된다.

## M2. SWEA 자동 기록

제안서 단계 3에 대응한다.

포함 범위:

- 문제 페이지 감지와 문제 번호·제목·난이도 수집
- 코드 편집기 분석과 제출 결과 감지
- IndexedDB 저장과 기존 기록 병합
- 제출 후 AI 활용 빠른 입력

종료 조건:

- 개인정보를 제거한 DOM fixture와 실제 브라우저 시나리오로 검증한다.
- 문제/코드/결과 수집 성공률 목표의 표본과 계산법이 정의된다.
- 수집 실패 시 로그와 수동 입력 대체 경로가 동작한다.
- 플랫폼 DOM 변경이 공통 기능에 미치는 영향을 격리한다.

## M3. 기록 관리와 내보내기

제안서 단계 4에 대응한다.

포함 범위:

- 문제 목록, 상세, 검색과 필터
- AI 활용 수준 표시
- 언어 및 Java 클래스명 기반 파일명 생성
- 소스, README, Markdown, JSON 내보내기

종료 조건:

- 확장자 정확도, 다운로드, IDE 열기와 JSON 재가져오기를 검증한다.
- AI 기록 포함 여부와 공개 범위를 사용자가 통제한다.
- 생성 결과와 원본 데이터의 정합성을 확인한다.

## M4. 프로그래머스 지원

제안서 단계 5에 대응한다.

포함 범위:

- 문제 정보, 함수형 코드와 제출 결과 수집
- 다국어 감지와 파일 내보내기
- 플랫폼 공통 어댑터 구조 검증

종료 조건:

- SWEA 전용 가정이 공통 계층에 누출되지 않는다.
- 프로그래머스 수집 성공률 목표의 표본과 계산법이 정의된다.
- 지원 언어별 정상·실패 fixture를 검증한다.

## M5. AI 코드 리뷰

제안서 단계 6에 대응한다.

포함 범위:

- 사용자 API Key 설정과 삭제
- 코드 리뷰, 풀이 요약, 복잡도 분석, 개선점과 복습 질문
- 풀이 중 AI 사용과 사후 리뷰의 분리
- 결과 수정과 저장

종료 조건:

- API Key가 로그, 내보내기와 저장소에 부적절하게 노출되지 않는다.
- 요청 전 전송 데이터를 확인하고 자동 실행은 기본 비활성화한다.
- 비용 제한, 오류, 취소와 재시도 동작을 검증한다.

## M6. 복습과 AI 활용 통계

제안서 단계 7에 대응한다.

포함 범위:

- AI 활용 기반 복습 우선순위
- AI 없이 재풀이 모드
- 풀이별 AI 활용 변화와 알고리즘별 통계

종료 조건:

- AI 미사용과 미기록 상태가 구분된다.
- 통계가 원본 세션 기록과 일치한다.
- AI 사용을 부정적 점수로 단순 환산하지 않고 재풀이 성과와 함께 제시한다.

## M7. 보조 연동

제안서 단계 8~9에 대응한다.

포함 범위:

- Notion용 Markdown, 클립보드 복사, 설정 URL 열기
- GitHub 인증, 저장소·경로 선택, 코드와 README 수동 업로드
- AI 활용 공개 설정과 커밋 URL 저장

종료 조건:

- 외부 전송 전 사용자 확인과 미리보기를 제공한다.
- 최소 권한과 토큰 저장 정책을 검증한다.
- GitHub 업로드 결과와 로컬 파일이 동일하다.

## M8. 플랫폼 확장

제안서 단계 10~11에 대응한다.

순서:

1. 정올: 문제·코드·결과 수집, `Main` 기반 파일 저장
2. LeetCode: 난이도·태그·다국어 코드, 영문 파일명

각 플랫폼은 독립 어댑터, fixture, 수동 대체 경로와 플랫폼 정책 검토를 완료해야 한다.

## M9. 고급 기능

제안서 단계 12에 대응하며 MVP 이후 후보 범위다.

- ZIP 일괄 가져오기
- Notion API 직접 연동
- 서버 동기화
- 여러 AI 제공자
- 외부 AI 대화 가져오기
- 주간 학습 리포트
- AI 의존도 변화 분석

사용자 검증과 변경 요청 승인 전에는 일정이나 구현을 확정하지 않는다.

## 스프린트 배치 원칙

- 한 스프린트에는 검증 가능한 사용자 가치 한 가지를 목표로 둔다.
- 다음 마일스톤 작업은 현재 마일스톤의 핵심 위험을 줄이는 조사 목적일 때만 제한적으로 착수한다.
- 구현, 검증, 기록을 별도 후속 단계로 미루지 않고 같은 스프린트 범위에 포함한다.
- 미완료 작업은 다음 스프린트로 자동 이동하지 않는다. 범위 축소, 분할, 차단 해소 중 하나를 결정한다.
- 실제 처리량이 축적되기 전에는 마일스톤별 스프린트 수를 예측값으로 고정하지 않는다.

## 마일스톤 공통 관문

- 기획: 범위, 제외 범위, 사용자 시나리오와 수용 기준 승인
- 구현: 아키텍처 및 보안 규칙 준수, 오류·복구 경로 포함
- 검증: 자동 테스트와 필요한 Chrome 수동 시나리오 통과
- 기록: README, 아키텍처, 데이터 모델, ADR, KPI 근거 갱신

모든 관문을 통과하기 전에는 마일스톤 완료나 KPI 달성을 선언하지 않는다.
